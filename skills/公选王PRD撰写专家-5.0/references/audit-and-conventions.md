# 原型逻辑体检标尺与研发默认基线规范

本规范分为三部分：第一部分用于 **Stage 1（审原型聊方案）**，第二、三部分用于 **Stage 2（撰写干净、高信噪比的正式 PRD）**。

---

## 第一部分：Stage 1 原型逻辑体检 6 维标尺

收到原型图、原型链接、会议纪要或口述想法后，动笔写 PRD 前必须先按以下 6 个维度做逻辑扫描，找出真正阻断开发或导致体验断层的漏洞：

### 1. 页面路径闭环检查（防断头路）
- 每个页面是否明确**从哪个入口进、携带什么关键条件、完成后跳去哪、取消/返回回哪**？
- 是否存在“孤岛页面”（画了页面但没有任何入口能跳过去）或“死胡同”（提交成功或失败后没有去向说明）？

### 2. 状态生命周期闭环检查（防幽灵状态与单向锁死）
- 核心业务对象的每个状态枚举，是否都有清晰的**产生条件（Create）➔ 流转动作（Update）➔ 终结归宿（End）**？
- 是否存在“筛选下拉框里有某状态（如`已驳回`、`分配异常`），但全流程没有任何操作或系统事件能触发该状态”？
- 是否遗漏关键逆向路径：用户提交后能否**撤回/修改**？后台审核不通过是**直接终结**还是**退回允许重提**？涉及超时规则时，计时起点、阈值与到期动作（仅打标提示还是自动流转状态）是否明确？

### 3. 跨端配展同源检查（防前后端断链）
- C 端（APP / 小程序 / H5 / 网页端）页面上动态展示的规则文案、功能开关、作答方式、时间限制、名额上限，在管理端是否有对应的配置页面与字段？
- C 端发生的操作结果（如交卷、撤回、申诉），管理端或教师后台在哪个列表、哪个字段承接查看与处理？

### 4. 多角色与数据权限边界检查（防越权与误复用）
- 涉及多角色（如：管理员 vs 教务 vs 授课教师 vs 学员）时，不能因两个角色的界面长得像就默认规则一致。必须逐一核对 **6 个差异点**：`可见数据范围`、`字段可见与脱敏`、`可操作按钮`、`可编辑字段范围`、`可执行的状态流转`、`弹窗提示文案`。

### 5. 占用冲突与历史数据隔离检查（防线上事故）
- 当管理端对基础配置（如策略、试卷、课程、模板）执行**编辑、下架、删除**时：
  - 若当前正被“未开始 / 进行中”的业务引用，是**硬拦截禁止操作**，还是**软下架（老任务继续用、新任务不可选）**？
  - 修改或删除后，**已产生的历史记录/历史成绩单**是否保持原快照不受影响？
- 多人协同场景（如多名教师抢单领取、学员撤回的同时管理员点审批）是否存在状态并发冲突，冲突时以谁为准？

### 6. 材料内部一致性检查（防前后打架）
- 原型不同页面或口述前后是否对同一概念使用了不同名称（如第 1 页叫`批改方案`、第 3 页叫`批改策略`；列表叫`停用`、弹窗叫`下架`）？
- 同一限制条件在不同位置是否数值冲突（如一处写`10秒自动保存`，另一处写`30秒保存`）？

### Stage 1 输出铁律
1. **合并同类项，控制数量**：只挑出真正影响产品方案和研发实现的重点问题（一般 3~8 条），按重要程度排序。
2. **必须带产品建议**：严禁只抛问题当甩手掌柜。每条问题必须给出 **`[产品建议]`**（如：`建议采用方案 A：已有关联进行中考试时禁止下架并提示关联ID；历史已完成记录保留原策略快照`），让用户只需回复“同意”或微调即可进入 Stage 2。
3. **严禁追问默认研发常识**：下述第二部分列出的“研发默认免写基线”，一律不得在 Stage 1 拿来向用户提问凑数。

## 第二部分：研发默认约定基线（0 字免写过滤网）

为保证 PRD 对前后端研发和 Coding Agent 具备极高信噪比，以下内容属于互联网团队**默认工程基线**。除非当前业务明确要求**打破默认规则**，否则在正式 PRD 中**一律 0 字免写，也绝不标为 `[待确认]`**：

| 默认基线领域 | 默认生效规则（PRD 正文免写） | 何时才需要写进 PRD（例外情况） |
| :--- | :--- | :--- |
| **网络与系统异常** | 断网、请求超时、HTTP 5xx 报错由前端请求层统一 Toast 提示，不改变业务状态 | 接口超时会导致业务状态改变（如 AI 批改超时自动转入`人工待批改`队列） |
| **防重与基础输入** | 提交/保存按钮点击后默认 Loading 防连点；常规文本输入默认去除首尾空格 | 涉及长耗时异步轮询进度条、或允许保留首尾空格的特殊代码编辑器 |
| **列表通用交互** | 默认复用系统标准分页器；点`重置`清空条件并恢复默认排序；常规空值展示 `--` | 需区分易混淆的 `0 分`（已出分得零分）与 `--`（未出分），或需瀑布流无限滚动 |
| **默认时间格式** | 管理端时间默认 `YYYY-MM-DD HH:mm:ss`；C 端常规展示按 UI 规范处理 | 业务强依赖特定精度（如倒计时精确到秒 `mm:ss`、排期仅按日期 `YYYY-MM-DD`） |
| **常规弹窗关闭** | 二次确认弹窗点击`取消`、右上角关闭图标或遮罩（按组件库默认），均关闭弹窗且不改数据 | 强阻断弹窗（明确要求隐藏关闭图标且禁止点遮罩关闭），或关闭时需自动存草稿 |

### 什么才是必须写透的「业务级异常」？
凡满足以下任一条件，必须用四要素（`触发条件` ➔ `业务状态与数据结果` ➔ `用户反馈提示` ➔ `后续处理与责任角色`）写清闭环：
1. **改变业务对象状态**（如：OCR 识别失败、AI 打分失败、自动分配教师失败）；
2. **影响用户核心权益或成绩/资金**（如：考试中途强制交卷、扣减次数后生成失败如何退回）；
3. **跨角色/跨端状态冲突**（如：点击领取瞬间已被其他教师领走，刷新当前行状态并提示`该服务已被领取`）；
4. **批量操作部分失败**（如：勾选 50 条批量上下架，必须写死是`全部回滚`还是`成功 N 条并汇总提示失败明细`）。

## 第三部分：页面元素、字段、状态与弹窗写法细则

### 1. 页面元素与交互合写规范
- 按页面实际视觉分区（如`顶部通栏`、`题目内容区`、`作答操作区`）组织，同一元素的**展示来源、显隐条件、点击动作、校验与反馈**紧贴写在一处。
- **纯展示无交互元素**：一句点明含义 + `常规展示`（如：`- **试卷标题**：展示当前试卷名称，常规展示。`），既让 UI/前端确认元素存在，又不产生废话。
- **跨端动态元素**：C 端受后台配置驱动的元素，必须指明后台源头页面与字段标准名，确保前后端与 Coding Agent 自动对齐数据契约。

### 2. 管理端列表字段规范（一字段一行）
- 列表字段统一用 **3 列清爽表**（`字段名` ｜ `数据来源 / 计算口径` ｜ `展示格式与特殊交互`）。
- **严禁合并独立字段**：不得把 `创建人 / 创建时间`、`学员姓名 / 手机号` 合并写成一行。若原型 UI 将姓名和手机号上下排在同一列展示，表格中仍拆分为两行独立定义，并在展示列注明`与[某字段]同列组合展示`。

### 3. 状态描述分级规范
- **简单二元开关（如：显示/隐藏、启用/禁用，且无复杂占用拦截）**：无需单拆三级小节画大表，直接内联在状态字段或操作按钮下用 2 行说明切换条件与生效结果。
- **核心多状态流转（≥ 3 个状态，或涉及多角色交接/占用拦截）**：
  - 跨端共享状态统一放在 `2.2 核心术语与全局状态字典` 的 **4 列状态流转表**中定义一次，单页仅写本页按钮显隐与触发动作；
  - 仅单页内部使用的多状态字段，在该页设独立三级小节放 4 列状态表；
  - 状态业务含义必须写清**“当前什么事已发生、什么事待发生”**，禁止用状态名解释状态名（如禁止写“待领取：表示处于待领取状态”）；筛选器里的 `全部` 属于查询条件，不得混入业务状态枚举。

### 4. 弹窗分级与文案自适应规范
- **原型已给出明确弹窗文案**：100% 保留原型的标题、正文（含 `{变量}` 占位符）及按钮原文；同一动作在不同状态下弹窗文案不同时（如`待领取时关闭` vs `处理中时关闭`），分别列出差异文案，不得用一句“二次确认”抹平差异。
- **输入为口述纪要或粗略草图（未画弹窗细节）**：不为常规确认框留待确认窟窿，直接按业务语境写出清晰准确的文案并标注 `[建议文案]`。
- **内联 vs 独立小节**：无表单项的确认弹窗直接缩进写在触发按钮下；含多个输入表单项或复杂校验的弹窗，可设同页三级小节并在触发按钮处精准引用章节号。
