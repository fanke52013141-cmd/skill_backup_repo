# 精炼 PRD 撰写规范

## 1. 规范目标

这套规范服务一个目标：让开发按目录定位到页面后，能直接知道“有什么、怎么展示、怎么操作、有哪些状态、特殊情况怎么处理”，不需要先读完一整份长文档。

核心口径：**先覆盖全部材料，再精简重复文字；普通规则短写，关键状态、弹窗、角色差异和特殊规则写透。**

### 1.0 材料覆盖与详略顺序

撰写前建立内部覆盖清单，逐项记录材料位置、页面 / 弹窗标识、端、角色、触发入口、状态或文案变体、正文位置及覆盖结论。页面、弹窗、抽屉、提示均需登记；引用公共规则也必须映射到对应条目。正式 PRD 默认不展示这份自检表。

先盘点，再写作，再逐项查漏，最后精简并复核。背景、常规返回和普通字段用短句；影响实现的状态释义与流转、条件分支、角色差异、校验及弹窗文案逐项展开。不得用统一篇幅或总字数目标压缩重要内容。

原型无法访问、截图不清或链接中页面读取不全时，说明已读范围，登记未读对象和影响。保留已知页面与弹窗及其待确认项；未取得材料不能声称已完成全量核对。

### 1.1 信息分配原则

| 信息类型 | 写法 |
| --- | --- |
| 普通展示、常规返回、无特殊限制的字段 | 一句说清含义；列表字段明确写“无特殊规则” |
| 状态、条件显示、权限、数据变化、跨页面影响 | 写清触发条件、表现、可操作项、结果和影响范围 |
| 点击、选择、切换、上传、提交等交互 | 直接跟在对应元素下，不另起一套重复描述 |
| 业务失败与异常 | 写清业务状态、用户反馈、后续处理和数据结果 |
| 通用技术异常、实现细节、UI 已确定的纯视觉细节 | 不主动展开 |
| 未确定的业务事实 | 标 `[待确认]`，不编造、不暗中选择一种规则 |

### 1.2 一条规则是否值得写

只要影响以下任一项，就必须写：

- 页面或字段是否存在、如何展示；
- 角色是否可见、可操作；
- 状态如何变化；
- 数据如何计算、保存、刷新或同步；
- 页面如何跳转，操作后有什么反馈；
- 历史数据、其他页面、其他端是否受影响；
- 业务失败后由谁处理、学员或用户是否被拦截。

与上述内容无关、开发按常规即可实现的描述，删除或一句带过。

### 1.3 PRD 明确不输出的内容

以下内容不是“可选风格”，而是输出硬约束：

- **不单列“本期建议实施范围”**：本次范围只写在“背景与范围”，不再在文末另开分期、优先级或建议实施范围章节。
- **不输出“关键验收场景”**：不写验收场景、验收标准、测试用例或测试清单；PRD 只定义应该做成什么样。
- **不逐页插入原型图**：不生成或逐页插入原型、线框图、UI 截图或交互稿；UI / 原型地址只在文档信息中出现一次。这只约束图和链接的呈现；必须读取材料，并用文字覆盖本次范围内原型中的每个页面、弹窗和差异变体。
- **不保留空章节**：没有内容的可选模块直接删除，不用空标题占位。

**待确认清单是保留项**：存在未决项时，必须在文末保留可追踪的待确认清单，集中写清事项、负责人和影响范围。

## 2. 文档顺序与前置信息

正文按以下顺序组织；没有内容的可选模块直接删除，不留空标题。

1. 文档标题；
2. 文档信息与版本记录；
3. 背景与范围；
4. 角色与专业词汇（有歧义时写）；
5. 业务流程图；
6. 跨页面全局规则（确有必要时写）；
7. 按业务模块、端、页面展开的正文；
8. 待确认清单（存在待确认项时写）。

不另设“本期建议实施范围”“关键验收场景”“逐页原型图片”章节。范围已在“背景与范围”说明；不交付验收清单或新绘原型，但必须交代已有原型中的页面与弹窗内容。

### 2.1 文档信息

用一张小表承载，不写成长篇项目说明。

| 字段 | 规则 |
| --- | --- |
| 文档版本 | 必填，如 `V1.0` |
| 文档状态 | 建议写：草稿 / 评审中 / 已确认 / 已归档 |
| 创建时间、最近更新时间 | 必填；未提供则写“待补充”，不得编造 |
| 产品负责人 | 必填；使用用户提供的姓名或角色 |
| 涉及人员 | 只列实际涉及的产品、业务、UI、开发、测试及负责人 |
| UI / 原型地址 | 有则提供一次可定位链接；不要逐页重复贴原型 |
| 关联文档 | 写清文档名、版本或链接；引用具体规则时定位到章节 |

版本变更时，用简洁记录说明：`版本｜更改时间｜更改内容｜更改人`。只写本次变化，不复制整篇历史。

### 2.2 背景与范围

最多优先回答四件事：

- 为什么做；
- 本次做什么；
- 本次不做什么；
- 涉及哪些角色和端。

背景不展开行业论述、用户研究或价值论证；那些属于需求探索材料，不挤占开发 PRD。本节说完范围即止，不在文末另写“本期建议实施范围”或分期建议。

### 2.3 角色与专业词汇

- 多角色需求先列角色及其职责，例如“教务人员处理异常，学员只查看结果”。
- 只解释项目自定义、容易混淆或同名不同义的词汇。
- 状态词、业务 ID、特殊指标必须统一名称；不要在不同章节交替使用“停用 / 下架”“审核 / 确认”而不说明关系。
- 通用词汇不做字典式解释。

## 3. 流程图硬规则

流程图位于页面明细之前，是正式 PRD 的必备内容，不能用文字目录替代。

### 3.1 主流程

- 单角色：画从开始到业务终点的主流程，包含关键判断和失败分支。
- 多角色：必须表现角色分工，优先使用泳道图；工具不支持时按角色拆成多张图。
- 多端但业务角色相同：共用主业务流程，端差异放到对应页面说明。
- 有异步任务：画出“用户可离开、后台继续处理、结果如何回来”的路径。
- 有人工介入：画出谁处理、处理什么、处理后回到哪个状态。

### 3.2 图形与可交付形式

- 输出 Markdown 时可使用 Mermaid；正式协作文档中必须保证流程图实际可见，可插入飞书流程图或图片。
- 若只交付 Mermaid 源码，要提醒将其渲染或转成飞书流程图，不能把源码块冒充已经完成的视觉流程图。
- 节点使用业务语言，例如“AI 批改失败进入异常处理”，不要写技术实现细节。
- 页面跳转较多时，可另补页面流转图，但不能替代业务主流程。

### 3.3 信息不足时

只画已知流程，缺失节点标 `[待确认]`。不得因信息不全而省略整张流程图，也不得编造审批人、状态或分支。

## 4. 标题、编号与正文顺序

### 4.1 标题层级

正文最多三级：

| 层级 | 用途 | 示例 |
| --- | --- | --- |
| 一级标题 | 业务模块或端 | `# 四、正式考试模式（网页端）` |
| 二级标题 | 页面或独立流程 | `## 4.4 作答页面` |
| 三级标题 | 页面区域、字段组或子流程 | `### 4.4.1 顶部通栏` |

三级以下不再新增标题，改用粗体、无序列表或有序列表。

### 4.2 编号

- 章节号连续、唯一，并与标题层级对应。
- 不保留空章节；暂未撰写的章节必须标 `[待补充]` 并说明影响，不能只有标题。
- 新增或删除章节后，同步修正目录、交叉引用和流程图节点引用。
- 页面标题与正文引用使用同一页面名。

### 4.3 页面顺序

按真实业务使用顺序逐页撰写，不按“想到什么写什么”的顺序堆放。

常见端包括：网页端、APP 端、小程序端、管理后台、教师后台。只写本次涉及的端。

推荐顺序：

1. 先写支撑业务运转的配置与管理页面；
2. 再写用户从入口到业务终点的页面；
3. 最后写异常处理、补录、数据查看等分支页面；
4. 同一业务涉及多个端时，以“端 + 页面顺序”分别展开，并复用完全一致的规则。

## 5. 页面标准写法

### 5.1 页面开头

每个页面先用少量条目交代上下文：

```markdown
## x.y 页面名称

- **页面来源**：从哪个页面、点击哪个元素进入；返回时回到哪里。
- **页面定位**：一句话说明本页面完成什么业务任务。
- **权限 / 前置条件**：仅在有访问限制、角色差异或前置状态时填写。
- **页面去向**：存在多个关键去向时，写清分别进入哪个页面或流程。
```

简单页面可合并“页面来源 + 页面定位”，但不要省略页面与其他页面的逻辑关系。

### 5.2 页面元素与交互合写

默认结构：

```markdown
### x.y.z 区域名称

- **元素名称**：说明展示内容、输入内容或选项。
  - **显示 / 可用条件**：有状态或权限差异时填写。
  - **点击交互**：点击后的反馈、跳转、数据变化及二次确认。
  - **特殊规则**：只写影响开发判断的内容。
```

写法要求：

- 纯展示元素：一句说明展示什么；无特殊规则时不硬凑描述。
- 可点击元素：至少写“点击后发生什么”，不能只写“支持点击”或“点一下”。
- 普通返回、关闭等无特殊交互：一句写完，例如“点击后返回上一页，无其他限制”。
- 输入元素：按需写必填、默认值、选项、格式、长度、校验及错误反馈；没有的维度不逐项凑模板。
- 动态元素：写清何时出现、何时隐藏、切换后已有数据如何处理。
- 简单弹窗、抽屉、Toast 等反馈直接放在触发元素下；复杂弹窗可设三级小节，触发元素定位引用，正文只维护一份规则。
- 每个已画页面和弹窗都必须说明；不同角色、状态、文案或操作结果的变体必须分别说明或明确列差异。最短说明也必须保留入口、实际内容与操作结果，不能只写“弹出二次确认”。

弹窗记录按材料实际内容填写：

| 项目 | 要求 |
| --- | --- |
| 标识与入口 | 弹窗名称 / 标识、触发页面与元素、适用角色和状态 |
| 内容 | 标题、正文、按钮文案按原型原文保留，保留变量占位符和差异文案；原型明确无标题时写无标题 |
| 表单 | 如有输入项，逐项写默认值、必填与校验及反馈；没有则不添加 |
| 确认 | 写清校验、数据 / 状态变化、页面去向及已提供的反馈 |
| 取消与关闭 | 写已提供的取消、关闭按钮、遮罩或返回行为及输入是否保留；未提供的方式不猜测 |
| 未知 | 原文缺失或不可读时，按具体标题 / 正文 / 按钮 / 结果标待确认，不能删掉整个弹窗 |

共用布局时可引用一个基准弹窗，但每个差异变体都需有入口、差异文案与行为结论。禁止用“文案见原型”“同类弹窗略”替代。

- APP 端尤其要写清点击、返回、切换、手势、拍照 / 上传、录音及页面离开后的处理；无特殊交互时仍一句带过，不另写空泛的交互章节。

## 6. 列表与字段硬规则

### 6.1 列表页先交代的规则

按实际涉及情况写：数据范围、默认排序、搜索 / 筛选、分页或加载方式、权限、状态、操作列。没有特殊要求的项目一句说明或省略，不展开通用设计。

### 6.2 每个字段都必须有定义

字段不能只列名称。至少写清“含义或数据来源”，再补特殊规则。

管理后台和教师后台列表默认使用字段表，每个独立字段必须独占一行。禁止把“创建人 / 创建时间”“名称、手机号”合成一个字段说明。UI 在同一列组合展示多个独立信息时，仍逐字段定义，并注明所属展示列。一个字段自身有多个组成部分（如一个时间范围值）时可以解释其内部结构，但不得把原型中的两个独立字段改称复合字段。

| 字段名 | 含义或来源 | 展示与特殊规则 |
| --- | --- | --- |
| 创建人 | 创建本记录的人员姓名 | 无特殊规则 |
| 创建时间 | 本记录的创建时间 | 格式未提供则标待确认 |
| 服务状态 | 当前服务的业务阶段 | 展示固定枚举；引用本页“服务状态说明” |

先登记材料中的字段原名，写完后逐项核对，确保字段数及名称对应。规则较长时保留字段行，在独立小节展开并引用，不把多个字段挤进同一行。

```markdown
- **字段名**：字段含义或数据来源；展示格式；空值展示；特殊计算或交互。
- **普通字段**：展示对应信息，无特殊规则。
```

按需覆盖：

- 数据来源与统计口径；
- 展示格式、长度、精度、单位；
- 空值、为零、未提交等易混淆值；
- 枚举值与状态含义；
- 排序、截断、悬停、复制、下载等交互；
- 权限与可见范围；
- 无特殊要求时明确写“无特殊规则”，表示已经考虑过而非漏写。

后台列表保持一字段一行；其他页面按内容选择表格或字段列表。不把长规则挤成难读单元格，使用可定位的小节引用。

## 7. 状态说明硬规则

业务状态字段有两个及以上状态值时，必须在所属页面设独立三级小节“[字段名]状态说明”。跨页通用状态可设公共状态章节，但每页仍写本页展示、操作差异并定位引用。简单布尔显示标记可短写；业务状态不能因为只有两个值就当普通标记略过。

先确认状态名称和分隔，不凭模糊口述拆词，不把“处理中超过12小时”等提示擅自认定为独立状态。保留原始描述并标待确认。逐个状态首先解释**业务含义：对象现在处于哪个阶段，哪些事已发生、哪些尚未发生**，不能用状态名重复解释状态名。

每个状态至少回答：

1. **状态有哪些**：使用固定枚举值；
2. **如何进入**：初始状态、触发条件、操作或系统事件；
3. **页面表现**：文案、置灰、隐藏、颜色、Loading 等只写业务需要的部分；
4. **能做什么**：不同角色可见、可点、不可点的操作；
5. **如何离开**：成功、失败、人工处理后的去向；
6. **有什么影响**：历史数据、其他页面、其他角色和其他端是否变化。

每个状态可按表格行或独立条目组织；多分支用补充条目展开，不为了表格压缩规则。推荐列为：状态值、业务含义、进入条件、页面表现、各角色允许 / 禁止操作、退出条件与下一状态、数据与跨页影响。缺少哪一项就精确标哪一项待确认，不能用一条笼统待确认替代全部已知事实。

涉及超时必须说明计时起点、阈值和比较边界、是否重置、到期动作及目标状态；仅材料明确涉及的维度才展开，未明确的相关规则标待确认。不要把时间文案自动解释为撤回规则。

逐项对照字段展示枚举、筛选枚举和流转表；筛选中的“全部”等查询选项不是业务状态，要明确区分。差异必须有解释或待确认项。

## 8. 业务异常与权责边界

### 8.1 需要写的异常

- 业务流程失败：AI 打分失败、OCR 失败、语音转录失败、上传后仍不符合业务限制等；
- 权限或状态拦截：无权限、未开放、状态不允许操作；
- 会影响业务结果的技术失败：例如接口超时最终导致“打分失败”并进入人工处理；
- 会导致权责不清的情况：谁收到通知、谁处理、用户是否等待、能否继续、历史数据是否保留。

异常写法按实际涉及项组合：

```markdown
- **触发条件**：什么业务步骤出现什么结果。
- **业务状态**：试卷、题目、任务或页面进入什么状态。
- **用户反馈**：页面展示、按钮可用性和提示文案。
- **后续处理**：自动重试、人工审核、重新操作或终止。
- **数据与权责**：是否保留原数据、是否通知、由谁处理、处理后回到哪里。
```

### 8.2 默认不展开的内容

- 泛化的“网络失败怎么办”；
- 不改变业务流程的通用接口报错、并发、重试和服务器实现；
- 数据库表、接口 schema、技术架构；
- UI 已明确的纯视觉细节。

如果上述内容会改变用户路径、业务状态或责任归属，就只写其业务结果，不替技术设计实现。

## 9. 复用、引用与多端差异

允许复用，但必须可定位、可核对。

推荐写法：

```markdown
本页复用[文档名 / 章节号]的字段与交互规则，差异如下：
1. 差异项一；
2. 差异项二。
未列出的规则与基准章节一致。
```

要求：

- 引用到具体文档、版本和章节，不只写“参考原来的”；
- 用一句话概括被引用的核心规则，避免开发打开链接后仍需猜测；
- 多端或多角色只写差异时，必须明确基准端 / 角色与适用页面；
- 先逐项核对数据范围、字段可见性、按钮、可编辑范围、状态操作、弹窗与文案六类差异，再决定复用。用差异表或短条目记录结果；确认一致才写一致，未明确则标待确认；
- 每个角色在覆盖清单中保留映射，不能因为界面相似就删除其页面。布局一致但数据或操作不同的，明确共用部分及差异；
- 发现实际规则不同，不得继续使用“全部一致”；
- 页面内的特殊规则留在本页面，不因提取公共规则而让开发来回跳读。

## 10. 待确认与规则冲突

统一格式：

```markdown
[待确认：具体事项｜负责人：姓名或角色（未知可不填）｜影响：页面、字段或流程]
```

- 用 `[待确认]` 替代“XX”“到时候再说”“UI 确定”等无法追踪的写法。
- 规则冲突时不擅自选择一个版本；列出冲突位置、两种说法及影响。
- 评审后清除已解决的待确认项，并更新版本记录。
- 格式、编号和明显错别字可直接修正；业务数值、状态、权限和流程不得静默改写。

## 11. 语言与格式

- 使用短句，一条列表只表达一个主要规则。
- 优先使用确定表述：“当……时，……”“点击后……”“仅当……时显示”。
- 数值、单位、精度、枚举、提示文案尽量写准确。
- 避免“等等”“相关内容”“尽量”“同上”“参考一下”“按常规处理”等无法执行的词。
- 默认输出简洁 Markdown，便于粘贴到飞书云文档；不使用四级及以下标题。
- 不用大面积加粗制造视觉噪音，只强调字段名、状态名和关键限制。

## 12. 交付前验收

### 12.1 结构

- [ ] 文档信息、背景范围、涉及角色和端可快速定位。
- [ ] 页面明细前有实际可交付的主流程图；多角色已体现分工。
- [ ] 正文按端和业务页面顺序组织，最多三级标题。
- [ ] 编号连续，引用准确，无空章节。

### 12.2 页面与字段

- [ ] 原型中本次范围内每个页面、弹窗、抽屉、提示及角色 / 状态 / 文案变体都有对应说明；未读取部分明确披露。
- [ ] 每个页面有来源、定位及关键去向。
- [ ] 后台列表一字段一行，字段与材料逐项对应，没有合并独立字段；普通字段短写。
- [ ] 可点击元素都有点击结果，交互与元素写在一起。
- [ ] 多状态业务字段有独立小节，每个枚举有业务含义、触发、表现、角色操作、去向及影响；超时规则不靠猜测。
- [ ] 每个弹窗有原文或具体待确认项、按钮和结果，各变体差异完整。

### 12.3 特殊规则

- [ ] 权限、历史数据、跨端同步、异步处理和人工责任已写清。
- [ ] 业务失败有状态、反馈、后续处理和数据结果。
- [ ] 多端 / 多角色已核对六类差异；复用有基准、适用范围与差异，没有孤零零的“同上”。
- [ ] 未确定项均为可追踪的 `[待确认]`，没有编造或隐性冲突。

### 12.4 精炼度

- [ ] 删除重复描述、通用技术异常和与开发判断无关的背景。
- [ ] 没有“本期建议实施范围”、分期计划或优先级建议。
- [ ] 没有“关键验收场景”、验收标准、测试用例或测试清单。
- [ ] 没有逐页原型、线框图、UI 截图或重复的原型链接。
- [ ] 存在未决项时保留待确认清单，且事项、负责人、影响范围可追踪。
- [ ] 开发只看目录和对应章节，就能开始实现该页面。
- [ ] 精简前后均逐项核对覆盖清单；页面、弹窗、字段、状态、角色差异与权责没有被删除。
