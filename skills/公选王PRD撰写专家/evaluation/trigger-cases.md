# 公选王PRD撰写专家：触发回归用例

## 正例：应触发

| 用户说法 | 预期模式 | 关键动作 |
| --- | --- | --- |
| “把这份会议纪要整理成开发能直接看的 PRD。” | 新建 | 提取业务事实，先流程后页面，未知项标待确认 |
| “按我的精炼规范改写这份需求文档，不要写传统那种大而全。” | 改写 | 保留业务规则，重排目录，压缩普通描述 |
| “帮我检查这个 PRD，只看字段、状态、交互有没有漏。” | 审查 | 只给问题清单，不默认重写全文 |
| “这次只改考试列表页，帮我更新需求文档和版本记录。” | 增量更新 | 修改目标章节，检查交叉引用与受影响页面 |
| “这个小程序需求涉及学员和老师，先画两个角色的流程再逐页写。” | 新建 | 输出多角色流程，再按页面顺序撰写 |
| “把这几条语音笔记整理成飞书文档能粘贴的 Markdown 需求。” | 新建 | 输出简洁 Markdown，不堆传统 PRD 章节 |

## 反例：不应触发

| 用户说法 | 原因 |
| --- | --- |
| “帮我探索一下这个需求有没有价值，用户痛点是什么。” | 需求价值探索与用户研究，不是 PRD 撰写 |
| “把这个页面做成高保真可交互原型。” | 原型与设计任务 |
| “帮我设计订单服务的数据库表和接口。” | 技术设计任务 |
| “把这段话润色得更正式。” | 与 PRD 结构无关的通用文字润色 |

## 边界：应正确分流或组合

| 用户说法 | 预期处理 |
| --- | --- |
| “需求探索已经完成，现在把确认方案写成 PRD。” | 触发本 Skill；不重新做需求价值探索 |
| “先帮我判断需求，再决定要不要写 PRD。” | 先走需求探索；用户确认进入文档阶段后再用本 Skill |
| “根据这份 PRD 做原型。” | 原型任务为主；只有需要补写或审查 PRD 时才用本 Skill |
| “PRD 里的业务规则已经确定，请顺便补数据库设计。” | 本 Skill 只处理 PRD；数据库设计另行处理，不混入文档 |

## 执行回归点

- 多角色需求不能在页面明细前省略角色流程。
- 列表字段不能只列字段名，普通字段需明确“无特殊规则”。
- 可点击元素不能只写“支持点击”，必须写点击结果。
- 业务规则冲突必须标待确认，不能静默二选一。
- 用户只要求审查时不能覆盖原文或擅自交付全文改写稿。
- 通用网络、并发异常默认不展开；业务失败必须写状态与责任闭环。
- 需要浓缩示例时，不得只列一级 / 二级目录；必须覆盖 APP 页面、网页端列表页、管理后台列表页，且每类展示到三级标题。
