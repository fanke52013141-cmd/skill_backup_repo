## 1. 双层验证体系（执行结果验证 vs. 技能质量验证）

高质量技能必须同时具备“单次执行结果可验证”与“技能本身质量可迭代”两层验证机制：

### 1.1 A 层：执行结果验证（写入目标技能正文的验证清单）

在每个生成的 `SKILL.md` 末尾，必须提供可复制执行的验证清单，至少覆盖以下四个维度：

- **功能验证**：核心业务逻辑或代码转换是否达成预期目标（如运行单元测试命令 `pytest tests/`）。
- **构建与静态检查验证**：生成或修改后的代码/文档是否通过编译、类型检查与格式校验（如 `npm run typecheck`、`ruff check .`）。
- **风险与回归验证**：是否误改了非目标文件、是否破坏了原有接口契约或遗留了调试代码（如 `git diff --stat` 检查变更范围）。
- **输出完整性验证**：交付产物是否包含了要求的全部章节、文件或未处理项说明。

### 1.2 B 层：技能质量验证（用于中等及复杂技能的工程化维护）

针对团队共用的中等及复杂技能，在 `evaluation/` 目录中维护评测基准，重点监控四项核心指标：

- **触发准确率（Precision）**：被触发的会话中，真正属于本技能目标范围的比例（防乱触发）。
- **触发召回率（Recall）**：本应使用该技能的用户请求中，成功自动激活该技能的比例（防漏触发，目标 ≥ 90%）。
- **任务完成准确率（Pass Rate）**：在无需人工中途纠偏的情况下，一次走完流程并通过所有检查点的比例。
- **输出结构一致性（Consistency）**：同一请求重复运行 3 至 5 次，输出产物的结构、质量与耗时是否稳定。

## 2. 评估驱动的双轨对照闭环（With-Skill vs. Baseline）

要量化证明技能的实际增益，需在隔离上下文的新会话中执行双轨对照测试：

1. **实验组（`with_skill`）**：加载待测技能运行 `evaluation/` 中的测试提示词，记录输出文件、总 Token 消耗与耗时（`timing.json`）。
2. **基线组（`without_skill` 或 `old_skill`）**：在无技能（或挂载修改前的旧版技能快照）的独立会话中运行完全相同的提示词。
3. **计算净增益（Benchmark Delta）**：对比实验组与基线组的断言通过率差值、工具调用轮数差值与 Token 消耗差值。若某个技能让 Token 消耗翻倍但通过率仅提升 2%，说明指令存在严重冗余，需立即瘦身。

## 3. 客观断言（Assertions）编写与盲测对比方法

- **客观可验证原则**：断言必须能通过脚本或明确的可观测特征判定（如“输出的 JSON 包含 `summary` 与 `risks` 两个顶级数组字段”），严禁使用“输出质量较好”等主观模糊表述。
- **强制证据绑定（Grading with Evidence）**：判定断言通过（PASS）或失败（FAIL）时，必须引用实际输出中的行号、文本片段或文件检测结果作为证据。
- **剔除无效断言**：若某条断言在实验组与基线组中永远同时通过，说明模型原生已掌握该能力，应删减 `SKILL.md` 中对应的冗余说教。
- **双版本盲测（Blind Comparison）**：对比重构前后的两个技能版本时，隐去产物归属标签，交由评审模型或人工按统一维度盲评排版、可读性与实用性。

## 4. 12 项生成前自检清单（Self-Review Checklist）

在向用户输出最终技能文件前，逐条执行以下 12 项自检，任一项不通过必须先修正再输出：

1. **准入合理性**：这个需求真的适合写 Skill 吗？（是否更适合写全局 Rule 或单次回复？）
2. **描述双向完整**：`description` 是否同时写清了触发场景（含同义词）和明确排除范围？
3. **去黑话与防误触**：是否消除了内部黑话、过度泛化表述以及与相邻技能的误触发风险？
4. **背景外置合规**：是否已将大段背景与映射表移入 `references/`，保持正文纯粹为 SOP？
5. **代码外置合规**：是否已将复杂解析、扫描与校验逻辑移入 `scripts/`，避免塞满正文？
6. **复杂度匹配**：是否为简单任务选择了轻量模板，而没有强行套用重型模板？
7. **检查点覆盖**：关键步骤是否均包含了可验证的 Checkpoint 检查点？
8. **三态示例齐备**：是否提供了典型、边界、失败三类示例，且每个示例都附带了判断逻辑说明？
9. **高危操作保护**：删除、覆盖、DDL 或批量改写操作是否均包含确认、备份或回滚机制？
10. **验证方式可执行**：验证清单是否给出了可直接复制运行的命令或明确检查项？
11. **体积与引用深度**：正文是否控制在 500 行内，且所有外置文件均为单层引用深度？
12. **参数依据透明**：涉及超时、阈值、批量大小或重试次数时，是否给出了判断依据与推荐范围而非写死孤立数值？

## 5. 常见技能故障诊断与修复速查表

| 故障现象 | 核心根因 | 标准修复动作 |
| :--- | :--- | :--- |
| **技能无法上传或不被识别** | 主文件名大小写错误（如 `skill.md`）、目录内混入了 `README.md`、或 YAML 含 `< >` 符号 | 运行 `python3 scripts/validate_skill.py` 自动扫描并按报错修复 |
| **技能漏触发（Recall 低）** | `description` 使用了内部黑话、核心动作词未前置、或缺少用户口语同义词与文件后缀 | 按五要素公式重写 `description`，前置核心动作并补充口语触发词 |
| **技能乱触发（Precision 低）** | `description` 适用范围过宽，缺少负向排除边界 | 收紧技术栈与场景定语，并在末尾追加“不处理……”条款 |
| **执行中途跳步或漏掉检查** | 步骤缺乏明确 Checkpoint、正文过长稀释注意力、或给了多个平行选项无默认值 | 将正文压缩至 500 行内，每个关键 Step 补齐五要素微结构与唯一默认推荐 |
| **调用外置脚本时永久卡死** | 脚本中含有 `input()` 或 `[y/N]` 等交互式 TTY 等待 | 改造脚本接口，所有参数通过命令行 Flag 传入，并补齐 `--help` 说明 |
